# PostgreSQL no Neon

## Como fica a arquitetura

Navegador → frontend futuro na Vercel → API Node.js no Render → PostgreSQL no Neon. O Neon hospeda o banco, não o backend nem o site. Usuários acessam pela internet sem instalar nada. A configuração inicial e os planos gratuitos devem ser conferidos nos painéis dos provedores; não se presume cota, disponibilidade ou backup ilimitados.

## Criar o banco

1. No Neon, criar projeto PostgreSQL 17, escolhendo uma região próxima da API. Usar um projeto/branch de desenvolvimento enquanto estamos preparando o sistema.
2. Em Connect, selecionar banco e papel de conexão. Copiar a connection string pooled para DATABASE_URL e a conexão direta para DIRECT_DATABASE_URL no `.env` **local** ou nos campos secretos do Render.
3. Não postar as URLs aqui: elas incluem senha. A configuração não deve ser inserida em código frontend, arquivo versionado ou variável pública da Vercel.

Exemplo sem credenciais reais:

```dotenv
DATABASE_URL=postgresql://ROLE:SENHA@HOST-pooler.neon.tech/DB?sslmode=require
DIRECT_DATABASE_URL=postgresql://ROLE:SENHA@HOST.neon.tech/DB?sslmode=require
```

A aplicação normaliza conexões externas para sslmode=verify-full, sem desligar verificação de certificado. O pool tem no máximo cinco conexões por processo, conexão ociosa de 30 segundos e timeout de conexão de 15 segundos. Channel binding é habilitado no driver. Neon pode suspender compute conforme o plano; medir a retomada em homologação.

## Banco novo

```powershell
npm.cmd ci
npm.cmd run catalog:import
npm.cmd run dev
```

O importador executa a migração e carrega as 1.905 entradas e 4.631 links do pacote real 0.5.1 em transação. Não cria usuários de exemplo. Outra opção é executar schema.sql uma vez no SQL Editor do Neon antes da importação; não executar o snapshot sobre tabelas já existentes. Não misturar migrations SQLite com PostgreSQL.

## Histórico SQLite

O backend SQLite e a ferramenta `db:transfer-sqlite` foram removidos, incluindo
suas dependências nativas. A API atual usa somente PostgreSQL. Caso seja
necessário investigar a migração antiga, consulte o histórico Git; os arquivos
antigos não devem ser executados no banco atual.

## Decisões de compatibilidade

- IDs continuam inteiros positivos com GENERATED BY DEFAULT AS IDENTITY, permitindo transferência dos IDs existentes. Contadores são ajustados após a carga.
- Datas continuam TEXT ISO 8601 UTC e flags continuam INTEGER 0/1 para preservar o contrato da API. Não houve conversão implícita de strings de data em fuso local.
- JSON externo continua em TEXT com CHECK IS JSON, consultado por operadores JSONB quando necessário. Não foram criadas cópias JSON de personagens.
- E-mail e username usam citext para unicidade sem distinção de caixa. Busca de nomes usa ILIKE. Uma colisão de caixa no destino falha e reverte, sem descartar registros.
- As 90 relações são FKs reais, inicialmente imediatas. Podem ser deferidas explicitamente na carga, para referências circulares entre concessões/talentos. Regras CHECK continuam imediatas e RESTRICT de exclusão é preservado.
- Leituras de relatório usam transação repeatable read. Escritas transacionais usam conexão dedicada do pool e um advisory lock de aplicação por banco, preservando inicialmente a serialização do SQLite para evitar perdas em refresh/edições. Um cache de SELECTs existe somente dentro da transação, é invalidado por escrita/rollback e não atravessa requisições. É uma escolha conservadora, não uma promessa de escalabilidade ilimitada; particionar locks e medir carga é evolução posterior.
- Prévia de alteração usa savepoints e rollback real. IDs de relações com chave composta no relatório de remoções são strings compostas estáveis, sem depender de rowid.

## Verificação e segurança

TEST_DATABASE_URL deve apontar para um banco de testes separado, nunca para a produção. Sem credenciais Neon fornecidas/configuradas, não foi possível verificar autenticação, permissões, latência ou limites do seu projeto Neon. A compatibilidade executada é com PostgreSQL 17 real, não com uma simulação em memória.

## Registro histórico da migração

60 testes da suíte atual passaram: 17 de integração PostgreSQL, 5 de configuração e 38 de regras puras. Os testes específicos do SQLite anterior foram removidos e seus resultados históricos não contam como verificação PostgreSQL atual. Snapshot e sample-data.sql foram executados em PostgreSQL 17; a fixture transferiu 199 registros de 50 tabelas, comparados campo a campo, e preservou contador de identidade 10000. A imagem final iniciou com PostgreSQL, importou 1.905 entradas e restaurou o archive pg_dump em outro banco vazio. Build, tipos, formatação e auditoria npm passaram. O DBML foi gerado por introspecção, mas não foi renderizado no dbdiagram.io. Detalhes em resultado-neon.json.
